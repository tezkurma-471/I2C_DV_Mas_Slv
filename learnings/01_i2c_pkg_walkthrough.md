## 1. Project Architecture — Bird's-Eye View

The I2C verification project is structured as a **block-level UVM verification environment** for an I2C slave DUT. Before diving into any file, you must internalize this architecture:

```
+-----------------------------------+
|         i2c_pkg.sv                |  ← Vocabulary (params, enums, typedefs)
+-----------------------------------+
            ↑ imported by all
            
+----------------+    +----------------+
| i2c_master.sv  |    | i2c_slave.sv   |  ← Thin wrappers (top-level pins)
| (thin top)     |    | (thin top)     |
+----------------+    +----------------+
       |                     |
       ↓                     ↓
+------------------------+ +-------------------------+
|i2c_master_controller.sv| | i2c_slave_controller.sv |  ← The MEAT (FSMs)
|     (20 KB, FSM)       | |     (18 KB, FSM)        |
+------------------------+ +-------------------------+
         |                          |
         +----- SDA, SCL bus -------+
```

### Why Wrappers + Controllers?

`i2c_master` and `i2c_slave` are like the **plastic case** of a USB drive — pretty pinout, no logic.
`*_controller.sv` files are the **actual chip inside**.

**Wrapper exists so you can swap controller implementations without breaking the top-level interface.**
This is a standard hierarchy pattern in industry RTL.

### Why a Package?

`i2c_pkg.sv` is your **shared vocabulary**. Both design and testbench import it so when the testbench
says `CMD_START`, the design knows exactly what bit pattern that means. Packages eliminate
"magic numbers" scattered across files.

## 3. Package Structure — Section-by-Section

### Section 1 — General Parameters (lines 14-49)

```systemverilog
parameter int CLK_FREQ_MHZ = 50;
parameter int T_SCL_PERIOD = 500;   // 10 us / 20 ns = 500 clocks
parameter int T_SCL_HIGH   = 250;
parameter int T_SCL_LOW    = 250;
```

**Why this matters:** I2C is clock-synchronous, but **SCL is generated by the master from the system clock**.
- System clock: 50 MHz → 20 ns period
- I2C Standard Mode: 100 kHz SCL → 10 µs period
- **SCL period in system clock ticks = 10 µs / 20 ns = 500 ticks**

The master controller counts to 500 to generate one SCL period; counts to 250 for half-period.

#### Setup/Hold Times

```systemverilog
parameter int T_SU_STA = 10;   // Setup time for START
parameter int T_HD_STA = 10;   // Hold time for START
parameter int T_HD_DAT = 5;    // Data hold time
```

These come from the **NXP UM10204 I2C specification**. In Standard Mode, the spec requires
t_HD;STA ≥ 4 µs (= 200 ticks at 50 MHz). The code uses 10 ticks — much smaller.

⚠️ **Discrepancy worth flagging in interviews:**
> *"I noticed the setup/hold values are scaled-down for simulation throughput; in a real silicon
> implementation we'd use the spec-mandated values."*

### Section 2 — Enumerations (lines 57-94)

The most important enum:

```systemverilog
typedef enum logic [3:0] {
  CMD_NOP       = 4'h0,
  CMD_START     = 4'h1,
  CMD_STOP      = 4'h2,
  CMD_WRITE     = 4'h3,
  CMD_READ_ACK  = 4'h4,
  CMD_READ_NACK = 4'h5,
  CMD_REP_START = 4'h6,
  CMD_ABORT     = 4'h7
} i2c_cmd_e;
```

This is the **command interface** between the host CPU and the I2C master controller.
The CPU writes one of these 4-bit values into `REG_CMD`; the master FSM decodes to bus actions.

**Key insight:** I2C protocol primitives are **atomic actions** (START, STOP, send byte, receive byte).
A "full transaction" like "write 3 bytes to slave 0x50" is built by issuing a **sequence** of commands:
```
START → WRITE(addr+W) → WRITE(data1) → WRITE(data2) → WRITE(data3) → STOP
```

#### Status Enum

```systemverilog
STS_ACK, STS_NACK, STS_ARB_LOST, STS_TIMEOUT, STS_DONE, STS_ERR
```

`STS_ARB_LOST` is multi-master arbitration loss — but commented as *"not used in single-master."*
**Scope limitation to mention in interviews:** this is a single-master implementation.

### Section 3 — Register Map (lines 100-114)

```systemverilog
typedef enum logic [2:0] {
  REG_CTRL   = 3'h0,
  REG_CMD    = 3'h1,
  REG_STATUS = 3'h2,
  REG_DATA   = 3'h3,
  REG_ADDR   = 3'h4,
  REG_IRQ_EN = 3'h5,
  REG_IRQ_ST = 3'h6
} i2c_reg_e;
```

This is an **APB-like CSR (Control & Status Register) map**. Real I2C IPs (STM32, Raspberry Pi, etc.)
expose this kind of memory-mapped interface to the CPU.

🎯 **Career opportunity:** Every UVM verification engineer learns to verify register maps using
**UVM RAL (Register Abstraction Layer)**. Your project HAS a register map but probably doesn't
use RAL yet. Adding RAL is the cleanest upgrade you can do — and it's interview gold.

### Section 4 — Functions (lines 120-131)

```systemverilog
function automatic addr_byte_t build_addr_byte(
  logic [6:0] addr,
  i2c_dir_e   dir
);
  return {addr, dir};
endfunction
```

**Why address byte = {7-bit addr, 1-bit R/W}:** On the wire, I2C transmits 8 bits at a time.
The first byte after START is special: top 7 bits identify the slave, bottom 1 bit says
"I'm writing to you (0)" or "send me data (1)".

```systemverilog
function automatic logic is_valid_addr(addr_byte_t addr_byte);
  return !((addr_byte[7:4] == 4'b0000) || (addr_byte[7:4] == 4'b1111));
endfunction
```

**Reserved addresses:** Per NXP I2C spec, `0000xxx` and `1111xxx` are reserved (general call,
10-bit addressing, high-speed master code, etc.). This function rejects them.

## 5. Quiz — Answers & Deep Explanations

### Q1 — Why T_SCL_PERIOD = 500?

**Senior-engineer answer:**
- System clock = 50 MHz → period = 1/50 MHz = 20 ns
- I2C Standard Mode SCL = 100 kHz → period = 1/100 kHz = 10 µs
- Ticks per SCL period = 10 µs / 20 ns = **500 ticks**
- T_SCL_HIGH = T_SCL_LOW = 250 ticks (half-period each, symmetric in Standard Mode)

**Note:** In Fast Mode (400 kHz), the spec requires **asymmetric** high/low times
(t_HIGH ≥ 0.6 µs, t_LOW ≥ 1.3 µs), so the half-period assumption breaks.

---

### Q2 — `parameter` vs `localparam`

Both are **compile-time constants**. The difference is **override-ability**:

```systemverilog
module my_fifo #(
  parameter int WIDTH = 8,        // ← Caller CAN override
  parameter int DEPTH = 16
) (...);

  localparam int ADDR_W = $clog2(DEPTH);     // ← Derived, CANNOT be overridden
  localparam int ALMOST_FULL = DEPTH - 2;
endmodule
```

Caller can do:
```systemverilog
my_fifo #(.WIDTH(16), .DEPTH(64)) u_fifo (...);   // ✅ OK
```

But NOT:
```systemverilog
my_fifo #(.ADDR_W(10)) u_fifo (...);   // ❌ Compile error
```

**Rule of thumb:**
- `parameter` → "I expect callers to configure this." (public API)
- `localparam` → "This is derived or internal." (private impl detail)

**Defensive design:** Using `localparam` for derived values prevents callers from creating
inconsistent configurations. If someone could override `ADDR_W` independently of `DEPTH`,
your FIFO would silently break.

**Inside a package** (like `i2c_pkg.sv`), both behave identically since packages have no
instantiation parameters. Best practice: still use `localparam` for derived values like
`T_SCL_HIGH = T_SCL_PERIOD/2` to document the dependency.

**Interview trap:** *"Why use localparam over parameter inside a module that has no `#()`?"*
Answer: **documentation and future-proofing.** If parameters are later added to the module,
the localparams remain safely private.

### Q3 — Why enum sized [3:0] for 8 entries?

3 bits would technically fit. Using 4 bits is intentional for **three reasons**:

1. **Future-proofing.** Adding `CMD_SOFT_RESET = 4'h8` later doesn't require widening the
   field everywhere. With `[2:0]`, every signal holding this enum would need rework.

2. **CPU register alignment.** The `REG_CMD` register is likely 8 bits. Using 4 bits for the
   command leaves a clean 4-bit field for future flags (e.g., burst-length, repeat-count).
   A 3-bit command would leave an awkward 5-bit field.

3. **Defensive against undefined states.** If the CPU writes `4'hF` (an unused code), the FSM
   can detect "invalid command" and go to an error state. With 3 bits, every possible value
   is a valid command — no room to detect software bugs.

**Lesson:** Field widths are an **architectural** choice, not just "smallest that fits." Real
designers think about (a) future extensibility, (b) software alignment, (c) error detection.

### Q4 — 8-bit input passed to 7-bit parameter ⚠️

**WRONG common belief:** "The last bit becomes the R/W bit."

**What actually happens:** SystemVerilog **silently truncates** the input from 8 bits to 7 bits —
the **MSB is dropped**.

```systemverilog
logic [7:0] my_addr = 8'hAB;   // Binary: 1010_1011
result = build_addr_byte(my_addr, DIR_WRITE);
// Inside the function, addr becomes 7'h2B (binary: 010_1011)
// Return value: {7'h2B, 1'b0} = 8'h56
```

**You don't lose the R/W bit. You lose the top bit of the address silently.**

This is one of the **most dangerous** behaviors in Verilog/SV. Width mismatches don't error —
they truncate or zero-extend silently. Real bugs hide here.

**Defenses:**
- Use `logic` types consistently; let lint tools catch width mismatches.
- Synopsys VCS / QuestaSim flag this with lint warnings (e.g., `-Wlint=truncation`).
- In code review, always check that function arg widths match at the call site.

**Interview-grade answer:**

> *"The function declares its first argument as 7 bits. If a caller passes 8 bits, SystemVerilog
> silently truncates the MSB — no warning unless lint is enabled. The function would return an
> address byte built from the lower 7 bits of the input, with the original MSB lost. This is a
> classic width-mismatch bug that lint tools and code review should catch."*

### Q5 — `function automatic` vs `function`

**Default behavior in Verilog:** `function` has **static lifetime** — its local variables
are **shared across all calls**. This is a relic of 1980s gate-level thinking.

```systemverilog
// STATIC (default) — DANGEROUS for testbenches
function int counter();
  int count = 0;          // ← SHARED across calls!
  count = count + 1;
  return count;
endfunction

$display(counter());  // 1
$display(counter());  // 2  ← NOT 1!
$display(counter());  // 3
```

**With `automatic`** — each call gets a fresh stack frame, like a normal programming-language function:

```systemverilog
function automatic int counter();
  int count = 0;          // ← Fresh every call
  count = count + 1;
  return count;
endfunction

$display(counter());  // 1
$display(counter());  // 1
$display(counter());  // 1
```

**Why `automatic` in `build_addr_byte`:**
- Called from multiple parallel processes (sequence, scoreboard, monitor).
- If **static**, two concurrent calls would corrupt each other's locals → race condition.
- `automatic` makes it **reentrant** — safe for concurrent use.

**Rules for your career:**
- **Testbench code:** Always use `function automatic` and `task automatic`. Always.
- **Synthesizable RTL:** Functions are inherently static-friendly (no recursion in hardware),
  but `automatic` is still preferred for clarity and safety.
- **Class methods:** Automatic by default — no need to add the keyword.
- **Package functions:** Static by default — explicitly add `automatic` if used concurrently.

**Interview question that uses this:**
> *"You have a task called from 4 parallel `fork-join` threads with different arguments —
> what could go wrong if the task isn't automatic?"*

Answer: local variable corruption, shared state, race conditions, non-deterministic output.

### Q6 — `` `ifndef`` Include Guard

```systemverilog
`ifndef I2C_PKG_SV
`define I2C_PKG_SV

package i2c_pkg;
  ...
endpackage

`endif
```

**Mechanism:** Standard C-style include guard.
- First time `` `include "i2c_pkg.sv"`` happens → `I2C_PKG_SV` is undefined → body compiles, then `I2C_PKG_SV` is defined.
- Second time → `I2C_PKG_SV` already defined → entire body is skipped.

**Why needed:** Without the guard, two files both `` `include "i2c_pkg.sv"`` → compiler sees
the package declared twice → "duplicate package definition" compile error.

**Is it necessary for SV packages?** ⭐ **Depends on the compilation flow:**

- **File-list compilation** (`-f files.f`, list package ONCE): **guards are redundant.** Package
  compiles once; other files use `import` statements. **Modern recommended way.**
- **`` `include``-based flow** (older, EDA Playground, some Makefile flows): **guards are essential.**
  The same file may get textually inserted multiple times.

The presence of guards in `i2c_pkg.sv` suggests this project supports `` `include``-style flows
(likely for EDA Playground compatibility).

**Interview-grade answer:**

> *"Include guards prevent multiple textual inclusion of the same file. For SystemVerilog
> packages compiled through a file list with `-f`, they're often redundant — packages compile
> once and are `import`-ed elsewhere. But when using `` `include`` directives — common in
> EDA Playground or older make-based flows — guards are essential to prevent duplicate
> definitions."*

### Q7 — The `STS_ARB_LOST` Coverage Question

**Junior answer:** "Write a separate test for it."

**Senior-engineer thought process:**

1. **Is this dead code?** If the FSM never transitions to `STS_ARB_LOST`, this enum value is
   dead. **Dead code is a verification problem** — it inflates code coverage holes you can never close.

2. **Two valid approaches:**
   - **(a) Remove the enum value** if multi-master isn't a feature → cleaner, simpler, no hole.
   - **(b) Keep it and verify it** if multi-master IS a planned feature → build a multi-master
     testbench, create bus contention, observe arbitration loss.

3. **For this project, the right answer is (a) — DOCUMENT the scope.**

   In README:
   > *"Scope: Single-master only. Arbitration loss (STS_ARB_LOST) is reserved for future
   > multi-master support and is not exercised in the current test plan."*

   Plus a **coverage waiver/exclusion** in the coverage report.

4. **For interviews:**
   > *"It's a scope-excluded feature. I documented it as out-of-scope in the test plan and
   > added a coverage exclusion so it doesn't appear as a hole in coverage reports. If we
   > ever add multi-master support, this becomes a feature requirement to verify."*

**The lesson:** Coverage holes don't close by writing tests for things you don't care about.
They close by **scoping clearly** what's in/out of the verification plan.

### Q8 — Fast Mode (400 kHz) Changes

**Identified correctly:** `T_SCL_PERIOD`, `T_SCL_HIGH`, `T_SCL_LOW`.

**Two subtleties to add:**

1. **`CLK_FREQ_MHZ` does NOT change** — the system clock is still 50 MHz. Only SCL generation changes.
2. **In Fast Mode, T_SCL_HIGH ≠ T_SCL_LOW.** I2C spec requires asymmetric times:
   - t_HIGH ≥ 0.6 µs (~30 ticks at 50 MHz)
   - t_LOW ≥ 1.3 µs (~65 ticks at 50 MHz)
   - Total 125 ticks (since 50 MHz / 400 kHz = 125), split unevenly.
3. **Setup/hold times tighten too** — e.g., t_HD;STA from 4 µs (200 ticks) to 0.6 µs (30 ticks).

**Senior-engineer answer:**

> *"To add Fast Mode support, all SCL timing parameters and most setup/hold parameters
> change because the I2C spec defines mode-dependent timing budgets. A clean implementation
> wouldn't hardcode the values — it would parameterize by mode (`STANDARD`, `FAST`, `FAST_PLUS`)
> and have an internal lookup table that selects the right values. The package as-written
> supports only one mode at a time, which is a scope limitation worth flagging."*

**Design improvement opportunity for your internship:**
> *"Sir/Ma'am, I'd like to refactor the I2C package to support multi-mode operation via a
> mode parameter. This is a real engineering deliverable for my internship."*

## 6. Key Takeaways

### Conceptual

1. **Packages are the project's vocabulary.** They eliminate magic numbers and create a single
   source of truth shared by RTL and testbench.
2. **`localparam` is defensive design.** Use it for any value derived from other parameters to
   prevent inconsistent override.
3. **Enum widths are architectural choices.** Pick width for (a) extensibility, (b) software
   alignment, (c) error-state detection — not just "smallest that fits."
4. **Width mismatches in SV are SILENT.** Lint tools and code review are your only defense.
5. **`function automatic` is mandatory in testbenches.** Non-automatic functions have shared
   static state → race conditions in concurrent test environments.
6. **Coverage holes don't close by writing tests for irrelevant features.** They close by
   scoping the test plan clearly and waiving out-of-scope items.

### Career-critical

- **You will be asked these exact questions in interviews.** Q4 (silent truncation), Q5 (function
  automatic), and Q7 (scoping coverage) are *fundamental* SV/DV knowledge — gaps here filter you out.
