## 1. Functional vs Code Coverage — The Fundamental Difference

Before any covergroup syntax, internalize this distinction. **Interviewers test this first.**

| Aspect | **Code Coverage** | **Functional Coverage** |
|---|---|---|
| **Source** | Auto-generated by simulator from RTL | Hand-written by verification engineer |
| **Question it answers** | "Did my tests *execute* every line/branch/FSM state of the DUT?" | "Did my tests *exercise* every *meaningful scenario* the spec demands?" |
| **Types** | Line, branch, toggle, FSM, expression, condition | Covergroup, coverpoint, cross |
| **Granularity** | Implementation-derived (per-statement) | Spec-derived (per-feature) |
| **Closure means** | "RTL was exercised" | "Verification plan was exercised" |
| **Can it be 100% with bugs?** | YES — easily | YES, but much harder |
| **Who writes it?** | Nobody — it's free | DV engineer, from the test plan |
| **Where it lives** | Simulator flag (`+cover=bcst`) | `covergroup` blocks in SV/UVM code |

### The "Both Are Necessary" Insight

**Code coverage at 100%** means every line ran. It says NOTHING about whether the line ran with **interesting values**.

Example: an adder.
```systemverilog
assign sum = a + b;
```
Drive `a=0, b=0` once. Code coverage = 100%. Did you test overflow? Negative values? Maximum? **No.** That's what functional coverage is for.

**Functional coverage at 100%** means every spec scenario was hit. It says NOTHING about whether the RTL has dead code or unreachable branches.

Example: your RTL has a forgotten `else` branch the spec doesn't require. Functional coverage stays 100%; code coverage flags it as a hole — which leads you to either prune the dead code or scope it.

**Senior engineer rule:** Functional coverage drives the test plan. Code coverage drives the **completeness check** that the implementation matches the test plan.

**Interview-grade answer:**

> *"Code coverage measures structural execution of the RTL — lines, branches, FSM states, toggles — and is computed automatically by the simulator. Functional coverage measures whether the test plan's *intent* was hit — addressed scenarios, corner cases, protocol modes — and is hand-written as covergroups by the verification engineer. They're complementary: code coverage catches dead RTL, functional coverage catches missing tests. A signoff requires both at agreed thresholds, typically 100% functional and 95%+ code with documented waivers."*

## 2. The 60-Second Elevator Pitch

When an interviewer says: *"Walk me through the coverage in your I2C project."*

> *"I have a UVM subscriber class — `i2c_coverage` — that connects to the monitor's analysis_port. On every observed transaction, the monitor writes a `i2c_seq_item` to the subscriber. Inside `write()`, I sample 17 covergroups: 8 single-coverpoint groups covering direction, address ranges, data size, ACK/NACK, protocol flags, clock stretching, repeated-START depth, and 9 cross-coverage groups that catch interaction holes like read-with-stretch or write-with-NACK. Bin definitions are derived from the verification plan: I use range bins for burst sizes, explicit bins for specific addresses like the target 7'h50, and ignore_bins to suppress states that are logically handled by another coverpoint. The subscriber is registered in the env's connect_phase to the monitor's analysis_port. After the test, the report_phase prints per-covergroup percentages and raises a warning if average is below 90%, which is my signoff threshold for development; full closure is 100% per Verilog spec."*

Memorize the **shape**, not the words. Notice the structure: architecture → bins philosophy → wiring → reporting → closure threshold.

## 3. Coverage Class Architecture — How It Connects to the Monitor

```
+-------------------+          analysis_port           +-------------------+
|   i2c_monitor     |  -----------------------------> |  i2c_coverage     |
|  (extends         |   write(i2c_seq_item)            |  (extends         |
|   uvm_monitor)    |                                  |   uvm_subscriber) |
+-------------------+                                  +-------------------+
        |                                                       |
        | (observes SDA/SCL,                                    | calls cg.sample()
        |  builds seq_item)                                     | on every txn
        v                                                       v
   bus traffic                                            covergroup state
                                                          (bins fill up)
```

### Why `uvm_subscriber`?

`uvm_subscriber #(T)` is a UVM convenience class that:
1. Has a built-in `analysis_imp` (analysis implementation port) named `analysis_export`.
2. Declares a pure-virtual `write(T t)` you must override.
3. You connect it with `monitor.ap.connect(coverage.analysis_export);` in the env.

```systemverilog
class i2c_coverage extends uvm_subscriber #(i2c_seq_item);
```

The `#(i2c_seq_item)` type parameter tells the subscriber what kind of object will arrive via `write()`. Without it, the type is `uvm_object` and you'd need an awkward `$cast`.

### Why a Separate Coverage Class?

You **could** put covergroups directly in the monitor. **Don't.**

**Reasons to keep coverage in its own class:**
- **Separation of concerns.** Monitor observes; coverage measures. Two responsibilities, two classes.
- **Reusability.** Same monitor across multiple envs; each env can plug in different coverage policies.
- **Disable-able.** Coverage adds simulation overhead. You can disable the subscriber for regression "smoke" runs and enable it for "coverage-grade" runs.
- **Multiple subscribers.** Scoreboard, coverage, predictor, logger — all can subscribe to the same monitor analysis_port.

**Interview trap:** Engineers who put covergroups in the monitor will fail this question:
> *"How would you collect functional coverage on transactions the monitor sees, but also have a scoreboard see the same transactions?"*
Answer: analysis_port broadcast to multiple subscribers — monitor stays clean.

## 4. Covergroup vs Class — The Instantiation Pattern

This is a SystemVerilog quirk that confuses everyone the first time.

```systemverilog
class i2c_coverage extends uvm_subscriber #(i2c_seq_item);

  covergroup i2c_dir_cg;      // ← This is a TYPE declaration with implicit instance name
    cp_dir: coverpoint item.dir { ... }
  endgroup

  function new(string name, uvm_component parent = null);
    super.new(name, parent);
    i2c_dir_cg = new();       // ← You MUST explicitly construct it
  endfunction
endclass
```

### The Two-Step Dance

1. `covergroup ... endgroup` declares **both a type and an implicit member variable of that type** inside the class. The variable name equals the covergroup name.
2. `cg_name = new();` constructs the instance. **If you forget this step, you'll get a null-handle dereference when you call `sample()`.**

### Why Two Steps?

Covergroups need a **sampling context**. Inside a class, the implicit instance picks up the enclosing class's `this` for accessing member variables (like `item.dir` in the coverpoint expression). But the **timing** of construction matters — sometimes you want to construct the covergroup with arguments (e.g., to pass a clocking event):

```systemverilog
covergroup my_cg @(posedge clk);   // sampling on clk edge
  cp: coverpoint data;
endgroup

// You could do:
my_cg = new();   // implicit @(posedge clk) sampling
```

Or with a passed argument:
```systemverilog
covergroup my_cg (int width);
  cp: coverpoint data { bins b[width] = {[0:255]}; }
endgroup

my_cg = new(8);   // constructs with width=8
```

### The Bug You Will Hit Once

```systemverilog
function new(...);
  super.new(name, parent);
  // FORGOT: i2c_dir_cg = new();
endfunction

// Later:
i2c_dir_cg.sample();   // RUNTIME ERROR: null pointer
```

Symptom: simulation runs fine, **but the coverage report shows 0%** because `sample()` was never reached due to fatal null-pointer error (or you might see UVM_FATAL "null object access").

In `i2c_coverage.sv`, lines 230-249 are the explicit `new()` calls for every covergroup. **Count them — there should be exactly one `cg = new()` per covergroup.** Miss one → silent 0% on that covergroup.

```systemverilog
function new(string name = "i2c_coverage", uvm_component parent = null);
  super.new(name, parent);
  i2c_dir_cg       = new();
  i2c_data_size_cg = new();
  // ... 17 total
endfunction
```

### CG1 — `i2c_dir_cg` (Direction)

```systemverilog
covergroup i2c_dir_cg;
  option.per_instance = 1;
  option.name = "Direction";
  cp_dir: coverpoint item.dir {
    bins write = {DIR_WRITE};
    bins read  = {DIR_READ};
  }
endgroup
```

**Analogy:** A vending machine that tracks "customer bought a snack" vs "customer bought a drink." Two buckets, easy.

**What's being measured:** The DUT supports both read and write transactions. The verification plan demands you exercise both. This covergroup proves it.

**Annotation of every line:**
- `option.per_instance = 1` — track coverage per **instance** of this covergroup, not aggregated across all instances. Matters if you have multiple coverage subscribers (e.g., one per agent in a multi-master env). Default is 0 (type-level aggregation).
- `option.name = "Direction"` — human-readable label in the coverage report. Without it, the report shows the SV variable name.
- `cp_dir:` — label for the coverpoint. Lets you reference it in cross definitions later.
- `coverpoint item.dir` — the **expression** being sampled. `item` is the `i2c_seq_item` populated in `write()`. `dir` is the direction enum field.
- `bins write = {DIR_WRITE};` — explicit bin matching exactly `DIR_WRITE`. One transaction with `dir==DIR_WRITE` fills this bin.

**Why 2 explicit bins instead of auto-bins:** `item.dir` is an enum with values `DIR_WRITE` and `DIR_READ`. Auto-bins would create `auto[DIR_WRITE]` and `auto[DIR_READ]` — same count, ugly names. Explicit naming makes reports readable.

**Total bins:** 2. Closure means both bins hit at least once.

### CG2 — `i2c_data_size_cg` (Burst Length)

```systemverilog
covergroup i2c_data_size_cg;
  option.per_instance = 1;
  option.name = "Data Size";
  cp_size: coverpoint item.num_data {
    bins single = {1};
    bins short_burst  = {[2:8]};
    bins med_burst = {[9:16]};
    bins long_burst   = {[17:32]};
  }
endgroup
```

**Analogy:** Pizza delivery tracking "1 pizza," "2-8 pizzas (party)," "9-16 (large event)," "17-32 (catering)." You don't care about every exact count — you care about **size category**.

**Range bins syntax:** `{[lo:hi]}` matches any value in the inclusive range. `{[2:8]}` = 2, 3, 4, 5, 6, 7, 8 → all 7 values map to ONE bin.

**Why bucket?** `item.num_data` can be 1 to 32. If you used auto-bins, you'd get 32 bins requiring 32 hits. Most of those values are equivalent for verification purposes — testing 4 vs 5 bytes adds no new coverage. Bucketing reflects the **test plan's notion of "interesting boundaries."**

**The hole this exposes:**
What about `num_data = 0` (zero-byte transaction)? **Not in any bin → it's a "miss" but doesn't count as uncovered because no bin exists for it.** SystemVerilog **silently drops** sampled values that don't match any bin. This is a coverage *blind spot* if you forgot to define a bin for zero-byte transactions.

**Interview trap (Q12 below):** If you sample a value that doesn't match any explicit bin, **it doesn't count as a miss** — it just doesn't increment any bin. Auto-bins would catch this; explicit-only bins don't.

### CG3 — `i2c_addr_cg` (Address)

```systemverilog
covergroup i2c_addr_cg;
  option.per_instance = 1;
  option.name = "Address";
  cp_addr: coverpoint item.addr {
    bins target_addr = {7'h50};
    bins other_addrs = {[7'h08:7'h4F], [7'h51:7'h77]};
  }
endgroup
```

**Two range groups combined:** `{[7'h08:7'h4F], [7'h51:7'h77]}` — the comma inside the braces unions multiple ranges into one bin.

**Why 7'h08-7'h77?** I2C spec reserves 7'h00-7'h07 (general call, CBUS, etc.) and 7'h78-7'h7F (10-bit addressing, high-speed). The 0x50 address is the target slave; everything else (0x08-0x4F, 0x51-0x77) is "non-target traffic."

**Coverage hole exposed:** Reserved addresses 7'h00-7'h07 and 7'h78-7'h7F are **not** in any bin → if a test drives them, the sample silently drops. If you want to cover "DUT correctly NACKs reserved addresses," add `illegal_bins reserved = {[7'h00:7'h07], [7'h78:7'h7F]};` (more on this in §6).

### CG4 — `i2c_protocol_cg` (START, STOP, REP-START)

```systemverilog
covergroup i2c_protocol_cg;
  option.per_instance = 1;
  option.name = "Protocol";
  cp_start: coverpoint item.start_cond {
    bins has_start      = {1};
    ignore_bins no_start_ok = {0};
  }
  cp_stop:  coverpoint item.stop_cond  { bins has_stop  = {1}; bins no_stop = {0}; }
  cp_rep:   coverpoint item.rep_start  { bins has_rep   = {1}; bins no_rep  = {0}; }
endgroup
```

**Three coverpoints in one covergroup** — they share the same `sample()` call. Each transaction increments at most one bin per coverpoint.

**The `ignore_bins` on `cp_start`:**
- `start_cond == 1` → fresh START → `has_start`.
- `start_cond == 0` → no START (the transaction was a continuation after REP-START); it's not a hole, it's logically tracked by `cp_rep`. `ignore_bins` tells coverage tooling "**do not penalize me for not hitting this**."

**Critical concept — ignore_bins vs illegal_bins:**
- `ignore_bins` → "I know this state exists; it's expected; don't count against me." Excluded from the denominator.
- `illegal_bins` → "This state MUST NEVER occur; if you sample it, fire an error." Triggers a runtime warning/error.

The author used `ignore_bins` here because `start_cond=0` is **legal but uninteresting** for this coverpoint (interesting case is tracked via `cp_rep`).

**Bins on `cp_stop` and `cp_rep`:** both explicit `{0}` and `{1}` — every transaction will fall into one of them. Total bins per coverpoint = 2.

### CG5 — `i2c_ack_cg` (Address-phase ACK/NACK)

```systemverilog
covergroup i2c_ack_cg;
  option.per_instance = 1;
  option.name = "ACK Responses";
  cp_addr_ack: coverpoint item.addr_ack {
    bins ack  = {1};
    bins nack = {0};
  }
endgroup
```

**What "address ACK" means in I2C:** After the master sends the 7-bit address + R/W bit, the addressed slave pulls SDA low for one bit time = **ACK** (1 in our flag convention). If no slave responds (or wrong slave), SDA stays high = **NACK** (0).

**Verification value:** A test that only ever sees ACK means you never validated DUT behavior on NACK (timeout, retry, error reporting). This covergroup proves both polarities were exercised.

### CG6 — `i2c_burst_cg` (Cross: Direction × Size) ⭐ FIRST CROSS

```systemverilog
covergroup i2c_burst_cg;
  option.per_instance = 1;
  option.name = "Burst Cross";
  cp_dir: coverpoint item.dir;
  cp_size: coverpoint item.num_data {
    bins single = {1};
    bins short_burst  = {[2:8]};
    bins med_burst = {[9:16]};
    bins long_burst   = {[17:32]};
  }
  cross cp_dir, cp_size;
endgroup
```

**Cross coverage = Cartesian product of coverpoint bins.**

- `cp_dir` has 2 bins (DIR_WRITE, DIR_READ — auto-bins since no explicit bin block).
- `cp_size` has 4 bins (single, short_burst, med_burst, long_burst).
- `cross cp_dir, cp_size` creates **2 × 4 = 8** cross bins.

**The 8 cross bins:**
```
<DIR_WRITE, single>       <DIR_READ, single>
<DIR_WRITE, short_burst>  <DIR_READ, short_burst>
<DIR_WRITE, med_burst>    <DIR_READ, med_burst>
<DIR_WRITE, long_burst>   <DIR_READ, long_burst>
```

To close 100%, you need at least one transaction in each of the 8 combinations. **This is where coverage gets hard.** Easy to test write+single. Harder to test read+long_burst (32-byte read).

**Sneaky detail — `cp_dir` here has no explicit bin block:**
```systemverilog
cp_dir: coverpoint item.dir;   // ← no { ... }
```
For an enum, this auto-creates one bin per enum value. So `cp_dir` ends up with 2 bins named `auto[DIR_WRITE]` and `auto[DIR_READ]`. **The cross uses the auto-bin names** — not "write"/"read" as in CG1. Different covergroups, different bin names, even for the same field. Confusing in reports — be ready to explain.

### CG7 — `i2c_reg_ptr_cg` (Register Bank Coverage)

```systemverilog
covergroup i2c_reg_ptr_cg;
  option.per_instance = 1;
  option.name = "Register Bank Coverage";
  cp_reg: coverpoint item.num_data {
    bins single_reg      = {1};
    bins partial_bank    = {[2:4]};
    bins more_than_half  = {[5:7]};
    bins full_bank       = {8};
    bins multi_wrap      = {[9:32]};
  }
endgroup
```

**Note the comment from the file:**
> FIX BUG #13: Previous version covered item.data[0] value (0-255 data ranges) mislabeled as "Register Access". Since reg_ptr is internal to DUT and not exposed in seq_item, we cover burst length...

**Lesson from the bug:** You can only cover what's **visible** at the analysis-port interface. The internal register pointer (`reg_ptr`) of the DUT is not in the sequence item, so you can't directly cover it. The author worked around it by inferring register access pattern from burst length (writes start at reg 0, advance by 1 per byte).

**Interview gold:** "What if you wanted to cover internal DUT state directly?" → Answer: white-box coverage via **embedded covergroups in the RTL** (synthesizable? no — sim-only) or via **probe interfaces / bind statements** that hook signals from the DUT into the testbench.

**Why two `num_data` covergroups (CG2 vs CG7)?** Different **bucket boundaries** for different verification stories:
- CG2 (Data Size): generic burst categories (single, short, med, long).
- CG7 (Reg Bank): register-bank semantics — full bank = 8 bytes (the DUT has 8 registers), multi_wrap = beyond the bank.

Same field, two interpretations, two covergroups. **Acceptable design** — but redundant if you don't justify the distinction in the verification plan.

### CG8 — `i2c_target_cg` (Cross: Target Address × Direction)

```systemverilog
covergroup i2c_target_cg;
  cp_addr: coverpoint item.addr { bins target = {7'h50}; }
  cp_dir: coverpoint item.dir;
  cross cp_addr, cp_dir;
endgroup
```

**`cp_addr` has ONE bin (target).** `cp_dir` has 2 auto-bins. Cross = 1 × 2 = **2 cross bins**.

**Why is this even a cross?** Because `i2c_target_cg.sample()` is **conditionally called** in `write()`:
```systemverilog
if (t.addr == 7'h50) i2c_target_cg.sample();
```
So only target-address transactions ever sample this. The 2 cross bins are `<target, write>` and `<target, read>` — both must be hit for closure. Simple but explicit: "did we exercise both read and write on the target slave?"

**Interview discussion:** This is a degenerate cross (1×N). It could equivalently be a single coverpoint `cp_dir` sampled only when `addr==0x50`. The cross form is **declarative** — clearer in coverage reports that the intent is "target × direction."

### CG9 — `i2c_byte_nack_cg` (Per-Byte NACK Flag)

```systemverilog
covergroup i2c_byte_nack_cg;
  option.per_instance = 1;
  option.name = "Per-Byte NACK";
  cp_byte_nack: coverpoint has_data_nack {
    bins all_bytes_ack  = {0};
    bins data_nack_seen = {1};
  }
endgroup
```

**`has_data_nack` is a class member** (line 15) computed in `write()`:
```systemverilog
has_data_nack = 0;
foreach (t.byte_ack[i]) if (t.byte_ack[i] == 1'b0) has_data_nack = 1;
```

**This pattern is critical: derived coverage flags.**

The raw data — `t.byte_ack[]` queue — is a list of per-byte ACK responses. You can't directly coverpoint a queue. So you **reduce it to a scalar** before sampling: "was any byte NACKed?"

**Could you cover each element of the queue?** Yes, but it gets ugly:
- One coverpoint per index → wrong, queue length is dynamic.
- A loop in `sample()` calling `cg.sample()` once per byte → possible but disconnects per-byte from per-transaction semantics.

**Cleanest approach:** scalar reduction (`OR` of all elements) for "did NACK ever happen" + a second covergroup for per-byte-position NACK if needed. The file uses the former.

### CG10 — `i2c_stretch_cg` (Clock Stretching)

```systemverilog
covergroup i2c_stretch_cg;
  cp_stretch: coverpoint item.stretch_seen {
    bins no_stretch       = {0};
    bins stretch_seen_bin = {1};
  }
```

**Clock stretching** in I2C: a slow slave holds SCL low to pause the master while it processes data. Master must wait until slave releases SCL.

`item.stretch_seen` is presumably set by the monitor when it observes SCL held low > `T_SCL_LOW + 10` cycles by the slave. Coverage proves both polarities (normal timing, stretched timing) were exercised.

### CG11 — `i2c_rep_depth_cg` (Repeated-START Chain Depth)

```systemverilog
covergroup i2c_rep_depth_cg;
  cp_depth: coverpoint item.num_rep_starts {
    bins no_rep   = {0};
    bins one_rep  = {1};
    bins two_rep  = {2};
    bins deep_rep = {[3:$]};
  }
endgroup
```

**The `{[3:$]}` syntax** — the `$` token means "max value of the coverpoint's type." If `num_rep_starts` is `int`, this is `[3:2^31-1]`. In practice it's "3 or more."

**Why depth matters:** A single REP-START is common (write-address-then-read pattern). Two REP-STARTs is rare (multi-segment transaction). Three or more is a torture test for the master state machine. The bins reflect that **risk increases with depth** → distinct buckets for distinct test cases.

**Hole this exposes:** if every test only does ≤1 REP-START, `two_rep` and `deep_rep` show 0% → directed test required to close.

### CG12 — `i2c_dir_addr_cross_cg` (Cross: Direction × Address Range)

```systemverilog
covergroup i2c_dir_addr_cross_cg;
  cp_dir: coverpoint item.dir;
  cp_addr_range: coverpoint item.addr {
    bins target     = {7'h50};
    bins low_range  = {[7'h08:7'h4F]};
    bins high_range = {[7'h51:7'h77]};
  }
  cross cp_dir, cp_addr_range;
endgroup
```

**Cross bin count:** 2 (dir) × 3 (addr_range) = **6 bins**.

**The interaction this catches:** "We tested reads only on the target address; what about reads on non-target addresses (which the DUT should NACK)? We tested writes everywhere; good. We tested high-range addresses only with writes; missing read+high_range."

This is the **textbook reason** crosses exist — they catch **interaction holes** that individual coverpoints miss.

### CG13 — `i2c_dir_ack_cross_cg` (Direction × ACK)

```systemverilog
covergroup i2c_dir_ack_cross_cg;
  cp_dir: coverpoint item.dir;
  cp_ack: coverpoint item.addr_ack {
    bins ack  = {1};
    bins nack = {0};
  }
  cross cp_dir, cp_ack;
endgroup
```

**Cross bins:** 2 × 2 = **4 bins**. All 4 combinations must be hit:
- `<write, ack>` — write to target, slave ACKs → most common.
- `<write, nack>` — write to wrong address, slave NACKs.
- `<read, ack>` — read from target, slave ACKs address.
- `<read, nack>` — read attempt rejected.

**This is what a senior engineer means by "test the corners."** Not just "drive read and write" — drive each in the success path AND the failure path.

### CG14 — `i2c_rep_dir_cross_cg` (Repeated-START × Direction)

```systemverilog
covergroup i2c_rep_dir_cross_cg;
  cp_rep: coverpoint item.rep_start {
    bins no_rep  = {0};
    bins has_rep = {1};
  }
  cp_dir: coverpoint item.dir;
  cross cp_rep, cp_dir;
endgroup
```

**Cross bins:** 2 × 2 = **4 bins** — but the **interesting** ones are:
- `<has_rep, write>` — write segment after a REP-START (read-then-write pattern).
- `<has_rep, read>` — read segment after a REP-START (write-then-read pattern, classic I2C register read).

The non-rep variants are trivial. The rep variants are where bugs hide.

### CG15 — `i2c_dir_size_cross_cg` (Direction × Size, refined buckets)

```systemverilog
covergroup i2c_dir_size_cross_cg;
  cp_dir: coverpoint item.dir;
  cp_size: coverpoint item.num_data {
    bins single  = {1};
    bins small   = {[2:4]};
    bins medium  = {[5:8]};

    bins xlarge  = {[17:32]};
```

**Cross bins:** 2 × 5 = **10 bins**.

**Different bucketing than CG6** — finer-grained size categories. CG6 had 4 size bins; this one has 5. **Justification:** the verification plan distinguishes "small (2-4)" from "medium (5-8)" because the DUT's register bank is 8 deep — boundary at 4 vs 8 matters for off-by-one bugs.

**Cross-redundancy hazard:** CG6 (Direction × 4 size buckets) and CG15 (Direction × 5 size buckets) overlap significantly. **Pick ONE bucket scheme in production** unless you can justify both in the test plan. Keeping both inflates coverage maintenance.

## 6. Bins — Every Flavor with Examples

### 6.1 Auto Bins (Default Behavior)

```systemverilog
cp_x: coverpoint item.x;   // No { ... } block → auto-bins
```

**For enums:** one bin per enum value.
**For integers:** depends on `option.auto_bin_max` (default 64). If the value range is ≤ 64, one bin per value. Otherwise, the range is split into 64 equal-width bins.

```systemverilog
cp_byte: coverpoint item.data;   // 8-bit field, 256 values
// → auto-creates 64 bins, each covering 4 values: auto[0_3], auto[4_7], ...
```

**When to use:** quick-and-dirty coverage of enums (one line of code → comprehensive coverage). Avoid for wide integers — bucket meaningfully via explicit bins.

### 6.2 Explicit Bins (Single Value)

```systemverilog
bins target_addr = {7'h50};
```

Matches one specific value. Most precise control.

### 6.3 Range Bins

```systemverilog
bins short_burst = {[2:8]};
```

Inclusive range. Any value in `[2,8]` increments this one bin. **Used heavily** when you care about categories, not individual values.

### 6.4 Multiple Ranges in One Bin

```systemverilog
bins other_addrs = {[7'h08:7'h4F], [7'h51:7'h77]};
```

Union of ranges into a single bin. Comma-separated inside `{...}`.

### 6.5 Bin Arrays (One Bin Per Value in Range)

```systemverilog
bins addr_each[]   = {[7'h08:7'h0F]};   // 8 bins, one per address
bins addr_grouped[4] = {[7'h08:7'h0F]}; // 4 bins, 2 addresses each
```

**Key syntax:**
- `bins x[] = {[lo:hi]};` — **one bin per value** in the range.
- `bins x[N] = {[lo:hi]};` — **N bins**, range split evenly.

Useful when you genuinely care about every value (e.g., addressing every register in a small bank).

### 6.6 Wildcard Bins

```systemverilog
wildcard bins addr_low = {7'b0000???};  // matches 7'h00 through 7'h07
```

`?` matches `0` or `1`. Used for **reserved-address patterns** or **mask-based matching**. Common in CPU instruction-coverage where opcodes have don't-care bits.

### 6.7 Transition Bins (FSM coverage)

```systemverilog
bins idle_to_active = (IDLE => ACTIVE);
bins error_recovery = (ERROR => IDLE, RESET);   // ERROR→IDLE or ERROR→RESET
bins long_chain     = (IDLE => ACTIVE => DONE);  // multi-step transition
bins repeat_active  = (ACTIVE [*3]);             // ACTIVE 3 times in a row
bins consec_states  = (S0 => S1 [*2:5]);         // S0→S1 with S1 held 2-5 cycles
```

**When to use:** FSM-state coverage. Don't just track "did each state get reached" — track "did each *transition* get exercised." A bug might be reachable only through a specific transition path.

**For your I2C project:** A transition bin on the master FSM's state (`IDLE → START → ADDR → DATA → STOP`) would catch state-graph holes. The seq_item doesn't expose FSM state, so you'd need to add a state probe via a bind-statement.

### 6.8 `default` Bin

```systemverilog
cp_x: coverpoint item.x {
  bins low  = {[0:10]};
  bins high = {[90:100]};
  bins others = default;   // catches any value not in low or high
}
```

**Behavior:** `default` is the "everything else" bin. **Does NOT count toward coverage closure** by default — it's diagnostic only. Use it to confirm you didn't forget a value.

### 6.9 `ignore_bins`

```systemverilog
ignore_bins reset_state = {0};
```

**Effect:** values matching `ignore_bins` are **excluded from coverage computation**. The bin doesn't appear in the percentage at all.

**Use case:** A value exists in the field but is intentionally not measured here (because it's covered elsewhere, or it's a reset state, or it's tracked via another coverpoint).

**File example:**
```systemverilog
cp_start: coverpoint item.start_cond {
  bins has_start = {1};
  ignore_bins no_start_ok = {0};   // legal but uninteresting here
}
```

### 6.10 `illegal_bins`

```systemverilog
illegal_bins reserved_addrs = {[7'h00:7'h07], [7'h78:7'h7F]};
```

**Effect:** if a sampled value matches, simulator **fires a runtime error**. Used for "this MUST NEVER happen" assertions baked into coverage.

**Difference from `ignore_bins`:**

| | `ignore_bins` | `illegal_bins` |
|---|---|---|
| Excluded from coverage % | Yes | Yes (it shouldn't happen) |
| Triggers error on hit | No | YES — simulation flagged |
| Semantic meaning | "Don't measure this" | "This is forbidden" |
| Typical use | Reset states, scope-excluded features | Spec violations, protocol illegals |

**Interview answer:**
> *"`ignore_bins` says 'skip this in measurement'; `illegal_bins` says 'fire an error if observed.' Same exclusion semantics for coverage percentage, very different runtime behavior. Use illegal_bins for spec violations you want the simulator to catch automatically — like reserved I2C addresses being asserted on the bus."*

## 7. Cross Coverage — Bin Explosion and How to Tame It

### 7.1 The Cartesian Product Rule

Cross coverage creates one bin per **combination of coverpoint bins**.

```systemverilog
cp_a: coverpoint a { bins a_bins[] = {[0:9]}; }      // 10 bins
cp_b: coverpoint b { bins b_bins[] = {[0:9]}; }      // 10 bins
cp_c: coverpoint c { bins c_bins[] = {[0:9]}; }      // 10 bins
cross cp_a, cp_b, cp_c;                              // 10 × 10 × 10 = 1000 bins
```

**That's 1000 transactions minimum** to close 100% (assuming uniform sampling). For a 1-million transaction regression, that's 0.1% of stimulus going to coverage — usually feasible.

But:
```systemverilog
cp_a: coverpoint a; // 256 auto-bins (8-bit)
cp_b: coverpoint b; // 256 auto-bins
cross cp_a, cp_b;   // 65,536 bins. Doomed.
```

### 7.2 Bin Explosion — The Career Trap

**The bug:** you wrote a cross between two 8-bit values. `cp.size` = 256 × 256 = 65,536 bins. Your regression hits 1% coverage and you can't figure out why.

**Symptoms:**
- Cross coverage stuck at <5%.
- Single coverpoints at 100%.
- Simulator slow (every sample updates 65K bin counters).

**Fixes:**

**(a) Bucket the underlying coverpoints first:**
```systemverilog
cp_a: coverpoint a {
  bins low  = {[0:127]};
  bins high = {[128:255]};
}  // 2 bins
cp_b: coverpoint b {
  bins low  = {[0:127]};
  bins high = {[128:255]};
}  // 2 bins
cross cp_a, cp_b;  // 4 bins ✓
```

**(b) Limit the cross with `binsof` / `intersect`:**
```systemverilog
cross cp_a, cp_b {
  // Only care about interesting combos
  bins critical = binsof(cp_a.low) && binsof(cp_b.high);
  // Ignore all other combos
  ignore_bins boring = !(binsof(cp_a.low) && binsof(cp_b.high));
}
```

**(c) Subset crosses:** instead of a full 3-way cross, do three 2-way crosses if pairwise interaction is enough.

### 7.3 Coverage Report Reading

When you read a coverage report and see "cross has 8 bins, 6 hit (75%)":
- 8 bins = `|cp_a| × |cp_b|` — verify the math.
- 2 unhit bins → identify which combinations missing → design a directed test.

**Example for `i2c_dir_ack_cross_cg`:**
- 4 bins: `<write,ack>`, `<write,nack>`, `<read,ack>`, `<read,nack>`.
- If `<read,nack>` is missing → write a test that reads from a non-existent address.

## 8. Sampling — Implicit Event vs Explicit `cg.sample()`

Three ways to trigger covergroup sampling.

### 8.1 Explicit Call

```systemverilog
covergroup my_cg;
  cp: coverpoint x;
endgroup

// Elsewhere:
my_cg.sample();   // sample NOW
```

**Used in this file.** Inside `write()`, the subscriber explicitly calls `cg.sample()` for each covergroup:
```systemverilog
virtual function void write(i2c_seq_item t);
  this.item = t;
  i2c_dir_cg.sample();
  i2c_data_size_cg.sample();
  // ... etc
endfunction
```

**Why explicit?** The trigger event is "a transaction arrived at the monitor." That's a software event (a function call), not a hardware edge. Explicit `sample()` is the only fit.

### 8.2 Sampling Event Clause

```systemverilog
covergroup my_cg @(posedge clk);
  cp: coverpoint x;
endgroup
```

The covergroup samples **automatically on every `posedge clk`**. No explicit call needed.

**Used for:** signal-level coverage tied to a clock domain. Common in RTL-embedded coverage (e.g., monitoring an internal bus).

### 8.3 Sample with Argument

```systemverilog
covergroup my_cg with function sample(bit [7:0] val);
  cp: coverpoint val;
endgroup

my_cg.sample(some_value);  // passes value at call time
```

**SystemVerilog 2012+ feature.** Lets you decouple the covergroup from class members — pass the value explicitly. Useful when sampling a transient value that isn't worth storing in a class member.

### 8.4 Sampling Timing Trap (Interview Question)

```systemverilog
// In monitor:
item.dir = DIR_READ;
cov.write(item);
item.dir = DIR_WRITE;   // ← if cov stored a HANDLE, this CORRUPTS the sample
```

**Bug pattern:** if the coverage subscriber stores the seq_item handle (not a copy) and the monitor mutates the item after `write()` returns asynchronously, the covergroup might sample stale or corrupted data.

**In this file:** `this.item = t;` stores the **handle**, but `write()` is **synchronous** — it returns only after all `sample()` calls complete. So as long as the monitor doesn't mutate `t` until `write()` returns, it's safe. Best practice nonetheless: have the monitor **clone** the item before passing it to the analysis port.

**Interview-grade answer (Q13 below):**
> *"In a UVM subscriber, `write()` is called synchronously by the analysis_port. As long as all `cg.sample()` calls happen inside `write()` before it returns, the data is stable. The hazard arises if the monitor reuses the same seq_item handle — clone in the monitor or copy in the subscriber to be safe."*

## 9. Coverage Options — `at_least`, `weight`, `option` vs `type_option`

### 9.1 `option.per_instance`

```systemverilog
option.per_instance = 1;
```

**Default = 0.** Means "aggregate coverage across all instances of this covergroup." If you have 4 agents each with a coverage subscriber, by default you see a single combined number.

**Set = 1:** each instance reports independently. Useful when you want per-agent visibility.

### 9.2 `option.name`

```systemverilog
option.name = "Direction";
```

Sets the **display name** in coverage reports. Otherwise the SV variable name (`i2c_dir_cg`) is used.

### 9.3 `option.at_least`

```systemverilog
option.at_least = 5;
```

**A bin must be hit at least N times to count as "covered."** Default = 1.

**Why?** Some scenarios are statistically flaky — one hit might be a fluke. Requiring multiple hits proves the scenario is **reliably reproducible**.

**Example:** `at_least = 100` on a "stress" coverpoint forces the regression to hit it 100 times before signoff, giving statistical confidence.

### 9.4 `option.weight`

```systemverilog
option.weight = 2;
```

**Default = 1.** A coverpoint's weight multiplies its contribution to the covergroup's overall percentage.

**Example:** in a covergroup with 3 coverpoints (weights 1, 1, 2), the third coverpoint contributes 50% of the group's score.

**Use case:** prioritize high-importance scenarios. Direction coverage might be `weight=1` (basic); deep REP-START coverage `weight=3` (high-priority).

### 9.5 `option.cross_auto_bin_max`

```systemverilog
option.cross_auto_bin_max = 16;
```

Limits the number of auto-generated cross bins. Defense against bin explosion when one of the cross's coverpoints has auto-bins.

### 9.6 `option` vs `type_option`

**`option`** — per-instance setting. Only affects this instance.
**`type_option`** — type-level setting. Affects all instances of this covergroup type.

```systemverilog
covergroup my_cg;
  option.per_instance = 1;      // this instance
  type_option.weight  = 5;      // all instances of my_cg type
endgroup
```

**Interview trap:** confusing the two. Senior engineers know `type_option` exists; juniors don't.

### 9.7 `option.goal`

```systemverilog
option.goal = 90;
```

Sets the **closure target** for this covergroup to 90% instead of the default 100%. Used when 100% is unachievable (some bins are very rare) and a documented relaxation is acceptable.

## 10. Coverage Closure Strategy — What's Acceptable, How to Drive Holes

### 10.1 Closure Thresholds — Industry Norms

| Project Phase | Functional Coverage Target | Code Coverage Target |
|---|---|---|
| Block-level dev | 80%+ | 90%+ |
| Block-level signoff | 100% (with documented waivers) | 95%+ |
| Sub-system | 95%+ | 90%+ |
| Top-level / regression | 90%+ | 85%+ |
| Tape-out | 100% functional, all waivers reviewed | 95%+, reviewed |

**The "with documented waivers" caveat is critical.** 100% raw coverage is almost never achievable. The signoff is **"100% minus approved exclusions, with each exclusion justified in the verification plan."**

### 10.2 Driving Remaining Bins

You're at 85%. The remaining 15% is hard. Strategies:

**(a) Coverage-driven directed tests.**
Read the report. Identify the missing bins. Write a directed test that specifically drives them.
```systemverilog
// Missing: <read, xlarge>
// Test:
i2c_seq_item.create_read(.addr(0x50), .num_data(32));
```

**(b) Constrained random with biased weights.**
Modify constraints to bias toward rare scenarios.
```systemverilog
constraint c_size {
  num_data dist {1 := 10, [2:8] := 30, [9:16] := 30, [17:32] := 30};
  // was: num_data dist {1 := 60, ...} → biased away from large bursts
}
```

**(c) Coverage hooks in sequences.**
Use `solve before` and weighted distributions to ensure rare combinations occur.

**(d) Coverage exclusions (waivers).**
When a bin is unreachable due to scope:
```systemverilog
ignore_bins arb_lost = ...;
```
And document in the verification plan WHY this is excluded.

### 10.3 The "Last 5%" Problem

The closing 5% takes 50% of the effort. **Common rookies' mistakes:**
- Random tests that never hit the corner → switch to directed.
- Cross bins unreachable due to logical impossibility → use `binsof`/`intersect` to ignore them.
- Bin definition too narrow (typo, wrong range) → re-read bins critically before chasing tests.

## 11. Reporting — UCDB, HTML, Threshold Checks

### 11.1 The In-File Reporting (`report_phase`)

```systemverilog
virtual function void report_phase(uvm_phase phase);
  real dir_cov   = i2c_dir_cg.get_coverage();
  real avg_cov   = (dir_cov + size_cov + ack_cov + burst_cov) / 4.0;
  `uvm_info(get_type_name(), $sformatf(...), UVM_LOW)
  if (avg_cov < 90.0) begin
    `uvm_warning(get_type_name(), $sformatf("Coverage is below 90%%: %0.2f%%", avg_cov))
  end
endfunction
```

**What this does:**
- `cg.get_coverage()` returns a **real** between 0 and 100, representing the covergroup's coverage percentage.
- The function computes an aggregate average across 4 main covergroups.
- Raises a `uvm_warning` if below 90% — **soft check**, not a fatal.

**Limitations:**
- Only checks 4 of 17 covergroups in the aggregate (CG1, CG2, CG5, CG6). The "extended" group (CG9-17) is printed but not checked.
- A `uvm_warning` doesn't fail the test. To make it a hard signoff, use `uvm_error` or `uvm_fatal`.

### 11.2 UCDB (Unified Coverage Database)

**The industry-standard coverage format.** Simulators (Questa, VCS, Xcelium) write coverage results to a `.ucdb` file at simulation end.

**Why UCDB?**
- **Mergeable.** Run 1000 random seeds; merge their `.ucdb` files into one. Final coverage = union of all bins hit by any run.
- **Tool-agnostic.** All major EDA tools read/write UCDB.
- **Granular.** Per-bin information preserved, not just summary numbers.

Typical flow:
```bash
# Each test produces a .ucdb
vsim -coverage -do "run -all; coverage save run1.ucdb; quit"

# Merge all runs
vcover merge merged.ucdb run*.ucdb

# Generate human-readable report
vcover report merged.ucdb -html -htmldir cov_report/
```

### 11.3 HTML Reports

Simulators generate browsable HTML reports showing:
- Per-covergroup percentages.
- Per-bin hit counts.
- Cross-coverage matrices (interactive).
- Lint-style "missing bin" annotations.

**What to look for in an HTML report:**
- Red cells = uncovered bins → directed-test targets.
- Bin hit counts → if a bin has 1 hit, it's flaky; increase `at_least`.
- Cross matrices → diagonal-pattern misses suggest constraint bias issues.

### 11.4 Threshold Enforcement in CI

Production teams enforce thresholds in their CI pipeline:
```bash
# After regression
vcover report merged.ucdb -text > cov.txt
awk '/Overall Coverage/ {if ($NF < 95.0) exit 1}' cov.txt
```

A coverage drop fails the build. **Coverage is treated as a first-class regression metric.**

## 12. Common Bugs — The 0% Coverage Trap and Friends

### 12.1 Bug: Coverage Class Never Connected to Analysis Port

**The symptom:** all covergroups report 0%. No warnings, no errors. Just zero.

**The cause:**
```systemverilog
// In env.connect_phase — FORGOTTEN:
// monitor.ap.connect(coverage.analysis_export);
```

Without the connection, `write()` is never called → `sample()` never fires → all bins stay empty.

**Why no error:** A `uvm_subscriber` with no connection is **legal**. UVM doesn't complain. The simulator runs to completion, prints "all bins 0%," and you waste 3 days debugging tests when the bug is in `connect_phase`.

**Defense:** In `coverage.build_phase` or `check_phase`, assert that `analysis_export` has at least one connection. Or — simpler — add a print of `get_n_inputs()` in `start_of_simulation_phase`.

### 12.2 Bug: Covergroup Declared But Not Constructed

```systemverilog
covergroup my_cg; ... endgroup

function new(...);
  super.new(...);
  // FORGOT: my_cg = new();
endfunction
```

Result: null-handle access on `my_cg.sample()` → UVM_FATAL.

### 12.3 Bug: Bin Doesn't Match the Sampled Type

```systemverilog
cp_x: coverpoint item.data {   // item.data is bit [7:0]
  bins low = {-10};            // signed value vs unsigned field — never matches
}
```

Silent miss. The bin never fills.

### 12.4 Bug: Sample Called Before Item Populated

```systemverilog
function void write(i2c_seq_item t);
  i2c_dir_cg.sample();         // ← samples item.dir BEFORE item = t
  this.item = t;
endfunction
```

The covergroup sees the previous `item` value (or the default). **Always assign before sampling.**

### 12.5 Bug: Sampling Race in Cross-Coverage

If two coverpoints in the same covergroup reference different class members that update at different times, you can sample mismatched values.

**Mitigation:** populate all class members **before** calling `sample()`. Treat `sample()` as the commit point.

### 12.6 Bug: Forgetting to Call `super.new` in Subscriber

```systemverilog
function new(string name, uvm_component parent = null);
  // FORGOT: super.new(name, parent);
  i2c_dir_cg = new();
endfunction
```

The UVM base class isn't initialized → `analysis_export` is null → connection fails (sometimes silently).

## 14. Quiz Answers — Senior-Grade Deep Explanations

### Q1 — Code vs Functional Coverage

**Definitions:**
- **Code coverage** = simulator-computed structural metric: lines, branches, FSM states, expressions, conditions, toggles. Free, automatic.
- **Functional coverage** = hand-written `covergroup` measuring whether **spec-defined scenarios** were exercised. Requires verification engineer effort.

**Examples of holes each catches:**

| Hole | Caught by Code Cov? | Caught by Func Cov? |
|---|---|---|
| RTL has an `else` branch never taken | YES | NO (if not in plan) |
| Test never sets `mode=FAST` | NO | YES (if you have a `mode` coverpoint) |
| Wide adder never overflowed | NO (line ran) | YES (if you have an overflow coverpoint) |
| FSM has a dead state | YES | NO (likely) |

**Interview-grade answer:**

> *"Code coverage tells me whether the RTL was structurally exercised — every line, branch, and state. Functional coverage tells me whether the verification plan's intent was hit — every protocol mode, address range, error condition. They're complementary. 100% code coverage with bugs is common; 100% functional coverage with dead code is also common. Signoff requires both — typically 100% functional and 95%+ code with documented waivers."*

### Q2 — Covergroup vs Class Instantiation

**Mechanism:**
1. `covergroup ... endgroup` declares a **type** AND an **implicit member variable** of that type, both named the same.
2. The member variable is initially **null**.
3. You must explicitly call `cg_name = new();` to construct the instance, typically in the class's `new()`.

**Why two steps?**
- Decouples declaration from construction. Lets you pass arguments to `new()` (e.g., sampling event, ports).
- Lets the constructor capture the enclosing class's `this` for accessing member variables in coverpoint expressions.

**Forgotten construction:**
- `cg.sample()` → null-pointer access → UVM_FATAL or simulator crash.
- Worse case: coverage class doesn't crash but no bins ever fill → 0% silent failure.

**Interview-grade answer:**

> *"A covergroup declared inside a class creates both a type and an implicit member variable of that type, initialized to null. The variable must be explicitly constructed with `cg = new()` in the class's `new()` method before any `sample()` call. Forgetting this either crashes the simulation on the first sample with a null-handle error, or — worse — if `sample()` is in a try-catch context, silently produces 0% coverage. It's the #1 reason a covergroup reports 0% on day one."*

### Q3 — Cross Bin Count Math

**For `i2c_burst_cg`:**
- `cp_dir: coverpoint item.dir;` — no explicit bins. `dir` is an enum with 2 values (DIR_WRITE, DIR_READ). Auto-bins = 2.
- `cp_size:` has 4 explicit bins.
- Cross = **2 × 4 = 8 bins**.

**If `cp_size` were 8-bit auto-binned (assuming `option.auto_bin_max = 64`):**
- `cp_size` auto-bins = 64 (since 8-bit has 256 values > 64, split into 64 buckets).
- Cross = **2 × 64 = 128 bins**.

If `option.auto_bin_max` defaulted to 256:
- Cross = **2 × 256 = 512 bins**.

**Interview-grade answer:**

> *"For this covergroup, `cp_dir` has 2 auto-bins from the enum and `cp_size` has 4 explicit bins, giving 2 × 4 = 8 cross bins. If `cp_size` were unbinned with 8-bit data, it would auto-create min(256, `option.auto_bin_max`) bins — typically 64 by default, ballooning the cross to 128 bins. This is exactly why explicit bucketing matters before crossing."*

### Q4 — `ignore_bins` vs `illegal_bins`

| | `ignore_bins` | `illegal_bins` |
|---|---|---|
| Semantic | "Skip in measurement" | "Forbidden — fire error" |
| Excluded from coverage % | Yes | Yes |
| Runtime error on hit | NO | YES (`uvm_error` or sim warning) |
| Typical use | Scope-excluded states, redundant coverpoints | Spec violations, protocol illegals |

**Example:**
```systemverilog
cp_addr: coverpoint addr {
  bins valid = {[0x08:0x77]};
  ignore_bins reset_state = {0x00};           // legal but uninteresting
  illegal_bins reserved_addr = {[0x78:0x7F]}; // MUST NEVER appear
}
```

**Interview-grade answer:**

> *"`ignore_bins` excludes values from coverage measurement without runtime check — used when a value is legal but tracked elsewhere or out-of-scope. `illegal_bins` excludes AND fires a runtime error if the value is ever sampled — used for spec violations like reserved addresses or forbidden state transitions. Same exclusion semantics for the coverage percentage; very different runtime behavior. For I2C, reserved addresses 0x00-0x07 and 0x78-0x7F should be `illegal_bins` because the DUT must NACK them — if the testbench ever drives them and the simulator doesn't catch it, you've missed a chance to find a bug."*

### Q5 — Sample Event vs `cg.sample()`

**Two alternatives:**

1. **Sampling event:**
   ```systemverilog
   covergroup cg @(posedge clk);
   ```
   Auto-samples on every `posedge clk`. Used for clock-domain RTL-embedded coverage.

2. **Explicit call:**
   ```systemverilog
   cg.sample();
   ```
   Used when the trigger is a function call, not an edge — like a UVM subscriber's `write()`.

**Why explicit in this file:**
The trigger is "a transaction completed at the monitor" — a software event delivered via analysis_port `write()` call. There's no clock edge to tie to; the natural fit is explicit `sample()`.

**A sampling event in this file would mean:**
- Tie to a clock edge → sample every cycle regardless of transaction completion → wrong granularity (you'd sample mid-transaction with garbage values).
- Tie to an internal event handle → possible, but adds a layer of indirection (monitor would need to trigger the event after building the seq_item).

**Interview-grade answer:**

> *"Two ways: a clocking event clause `@(posedge clk)` for cycle-by-cycle sampling, useful for RTL-embedded coverage; or explicit `cg.sample()` calls when the trigger is a software event like a UVM analysis_port write. For a transaction-based subscriber, explicit sampling is correct — the trigger is the completion of a monitored transaction, not a hardware edge, and `write()` is the natural place to call `sample()` since the item is fully populated at that point."*

### Q6 — Coverage Thresholds

**Functional:**
- Block-level signoff: 100% with documented waivers.
- Top-level: 95%+.
- Tape-out: 100% (all waivers reviewed and signed).

**Code:**
- Block-level: 95%+.
- Top-level: 85%+.
- Tape-out: 95%+ with waivers.

**Why not 100%?**
- **Some bins are unreachable** — RTL has defensive code for impossible states.
- **Some scenarios are excluded by scope** — multi-master arbitration in a single-master TB.
- **Some code is dead** — leftover from feature changes; should be removed but sometimes retained for back-compat.

The signoff is **"100% minus approved waivers, each justified."**

**Interview-grade answer:**

> *"For signoff, functional coverage targets 100% with documented waivers; code coverage targets 95%+. Raw 100% on either is rarely achievable in real designs because of unreachable defensive code, out-of-scope features, or dead branches retained for compatibility. The real metric is 100% minus approved exclusions, with each exclusion justified in the verification plan and reviewed by leads. A bin labeled 'unreachable' with no waiver document is a red flag — that means somebody hasn't done the analysis."*

### Q7 — Forgotten Analysis Port Connection

**What happens:**
1. Simulation starts normally.
2. Monitor builds seq_items and calls `monitor.ap.write(item)`.
3. The analysis_port's `write()` is a no-op because no subscriber is connected.
4. `i2c_coverage.write()` is **never called**.
5. None of the `cg.sample()` calls execute.
6. Coverage report at end: **0% on every covergroup**.
7. No error, no warning. Just zero.

**Detection:**
- Check connection count: `cov.analysis_export.get_n_inputs()` should be 1 if connected.
- Add a check in coverage's `start_of_simulation_phase` that fails if no connection.
- Verify in `env.connect_phase` that the connection line exists.

**Interview-grade answer:**

> *"If the analysis_port to subscriber connection is forgotten in connect_phase, the monitor still calls `write()` on its port, but the port has no subscribers, so nothing happens. The subscriber's `write()` is never called, no `sample()` happens, and every covergroup reports 0%. Crucially, no UVM error or warning fires — UVM doesn't require analysis_ports to have subscribers. The first symptom is 0% coverage on every covergroup, which is the #1 cause of 'why is my coverage zero' debugging sessions. Defense: in build_phase, register a check that asserts at least one connection at start of simulation."*

### Q8 — Auto-Bins vs Explicit Bins for Enums

**Auto-bins on an enum:**
- One bin per enum value. Bin names auto-generated (e.g., `auto[DIR_WRITE]`).
- Pro: zero typing.
- Con: ugly report names; can't combine values into categories.

**Explicit bins:**
- Hand-named bins. Can group multiple enum values into one bin.
- Pro: readable reports, semantic grouping.
- Con: more typing; must update when enum changes.

**When to use which:**
- **Auto-bins:** small enums (<8 values), no need to group, prototyping phase.
- **Explicit bins:** production code, when bin names matter for reports, when grouping is needed.

For `i2c_seq_item.dir` (2 enum values): both work. CG1 uses explicit (`write`/`read` — readable); CG6 uses auto (just `cp_dir: coverpoint item.dir;` — terse). **Inconsistency in this file** — pick one style and stick to it in production.

**Interview-grade answer:**

> *"For a 4-value enum, auto-bins create 4 bins with names like `auto[STATE_A]` — zero typing but ugly reports. Explicit bins let you rename for clarity and combine values into semantic categories like `bins active_states = {STATE_A, STATE_B}`. Use auto-bins for small enums where the names don't matter and you trust the type to be stable; use explicit bins in production code for readable reports and intentional grouping. The biggest auto-bin gotcha is on wide integer fields, where auto-bins create up to 64 bins by default — pile on a cross and you've created a 4000-bin coverage hole."*

### Q9 — Transition Bins for I2C Master FSM

**The current file doesn't use transition bins.** A natural addition:

```systemverilog
typedef enum logic [2:0] {
  IDLE, START, ADDR, DATA, STOP, ERROR
} master_state_e;

covergroup i2c_master_fsm_cg @(posedge clk);
  cp_state: coverpoint master_state {
    // Single-state bins
    bins states[] = {IDLE, START, ADDR, DATA, STOP, ERROR};
    // Normal transitions
    bins start_seq    = (IDLE => START => ADDR);
    bins single_byte  = (ADDR => DATA => STOP);
    bins multi_byte   = (ADDR => DATA [*2:32] => STOP);
    bins error_recov  = (ERROR => IDLE);
    // Illegal transitions
    illegal_bins skip = (IDLE => DATA);    // can't skip START/ADDR
    illegal_bins back = (STOP => DATA);    // can't restart without START
  }
endgroup
```

**Note the `[*2:32]`** — "DATA state held 2 to 32 cycles in a row" — captures burst lengths as state-repeat counts.

**Why this matters:** Pure state coverage proves "each state was reached." Transition coverage proves "the FSM walked each legal path." A bug in the `ADDR → DATA` transition (e.g., wrong byte alignment) might leave both states 100% covered but fail this transition's coverage.

**Interview-grade answer:**

> *"Transition bins capture state-to-state movements, not just state occupancy. For an I2C master FSM with states IDLE, START, ADDR, DATA, STOP, ERROR, I'd add bins like `(IDLE => START => ADDR)` for the happy path, `(ADDR => DATA [*2:32] => STOP)` for bursts, and illegal_bins for impossible transitions like `(STOP => DATA)`. Pure state coverage might show 100% with a broken transition silently bypassed; transition bins force the FSM to be exercised along every legal path. For the I2C project, this would require exposing the master FSM state via a probe or bind, since it's not in the seq_item."*

### Q10 — `option.weight` and `option.at_least`

**`option.weight`** — multiplies a coverpoint's or covergroup's contribution to the parent's aggregate score. Default = 1.

```systemverilog
covergroup cg;
  cp_basic: coverpoint x;      // weight = 1 (default)
  cp_critical: coverpoint y;
  cp_critical.option.weight = 5;  // counts 5x more
endgroup
```

If `cp_basic` is 50% covered and `cp_critical` is 100% covered, weighted average = (50×1 + 100×5) / (1+5) = 91.7%.

**`option.at_least`** — minimum hit count for a bin to be considered "covered." Default = 1.

```systemverilog
covergroup cg;
  option.at_least = 5;   // every bin needs 5+ hits
  cp: coverpoint x { bins low = {[0:9]}; bins high = {[90:99]}; }
endgroup
```

A single fluke hit doesn't count. Bin must be hit 5+ times.

**When at_least = 100:** stress-test scenarios where statistical confidence matters — e.g., a "back-pressure stall" condition that's randomly hit; requiring 100 hits ensures it wasn't just a one-time fluke.

**Interview-grade answer:**

> *"`option.weight` scales a coverpoint or covergroup's contribution to the aggregate percentage — useful for prioritizing critical scenarios; a `weight=5` on a corner-case coverpoint forces it to drive the overall metric. `option.at_least` requires a bin to be hit N times to count as covered, defaulting to 1. Setting `at_least=100` on rare/stress conditions ensures statistical reliability — a single fluke hit doesn't satisfy closure. Both options together let you tune the coverage closure goal beyond a flat 100% — for example, weighting critical bins heavily and requiring multiple hits on rare scenarios."*

### Q11 — 100% Code Coverage, DUT Bug Missed

**How is that possible?**

Code coverage proves every line ran. It does NOT prove:
- The line ran with **interesting** input values.
- The line ran in **interesting** combinations of state.
- The DUT's **output** was correct after the line ran.

**Concrete example:**
```systemverilog
// RTL
always @* begin
  if (mode == FAST)
    timer_limit = 125;
  else
    timer_limit = 500;
end
```

A test that exercises both `mode == FAST` and `mode != FAST` achieves 100% branch coverage. **But what if the spec required `timer_limit = 250` in FAST mode** and the RTL says 125? Code coverage doesn't know — it just sees the lines ran. **The scoreboard would catch this, but only if a checker was written and a relevant test was run.**

**Where functional coverage helps:**
- A coverpoint on `mode` + a cross with `timer_limit` would expose the missing `(FAST, 250)` bin.
- A coverpoint on "transactions per second" would reveal whether the timer logic was meaningfully exercised.

**Interview-grade answer:**

> *"Code coverage measures structural execution — every line ran. It says nothing about whether the line ran with correct input values, in interesting state combinations, or produced correct outputs. A test can hit every line and miss bugs in: corner-case values, multi-feature interactions, or output correctness (which is the scoreboard's job, not code coverage's). Functional coverage closes these gaps by encoding the spec's intended scenarios — protocol modes, address ranges, error conditions — as covergroups. Functional + code together prove both the spec was exercised AND the implementation was structurally walked; neither alone is sufficient."*

### Q12 — Debugging 0% Coverage

**Step-by-step:**

1. **Check the analysis_port connection.** In env's `connect_phase`:
   ```systemverilog
   monitor.ap.connect(coverage.analysis_export);  // ← does this exist?
   ```

2. **Check the subscriber `write()` is being called.** Add a `uvm_info` or counter in `write()`:
   ```systemverilog
   `uvm_info("COV", $sformatf("write() called, item=%s", t.sprint()), UVM_LOW);
   ```
   If never printed → `write()` not invoked → connection problem.

3. **Check covergroup construction.** Confirm `cg = new()` for every covergroup in the class's `new()`.

4. **Check `sample()` is being called inside `write()`.** Single-step or add prints before each `sample()`.

5. **Check the coverpoint expression resolves to a value.** A null reference (`item.dir` when `item` is null) causes silent miss.

6. **Check bin definitions match the sampled type.** E.g., if `item.dir` is enum and your bin is `{1}` (integer), the match may fail due to type mismatch.

7. **Check whether the test plan actually drives the bin values.** A test that always drives `dir=DIR_WRITE` will leave `read` bin at 0%.

8. **Inspect the UCDB.** Open the coverage report — even at 0%, the report shows which bins exist. If bins are missing → covergroup not constructed.

**Interview-grade answer:**

> *"0% coverage with tests passing is a wiring problem 90% of the time. My checklist: (1) verify the analysis_port → analysis_export connection exists in connect_phase; (2) add a print in `write()` to confirm it's called; (3) check every covergroup is constructed in `new()`; (4) check `sample()` is reached for each cg; (5) verify coverpoint expressions don't dereference null; (6) verify bin definitions match the sampled type; (7) inspect the UCDB to see if bins even exist or just aren't being hit. The most common single cause is step 1 — forgotten connection — followed by step 3 — forgotten `new()`."*

### Q13 — Sample Race Conditions

**The race:**

1. Monitor builds `seq_item_A` and calls `ap.write(seq_item_A)`.
2. Coverage subscriber's `write()` stores handle: `this.item = seq_item_A`.
3. Subscriber calls `i2c_dir_cg.sample()`. Coverpoint evaluates `item.dir == DIR_WRITE`. Bin filled.
4. **If write() were async**, the monitor might mutate `seq_item_A` before `i2c_data_size_cg.sample()` is called. The coverpoint would see the mutated value.

**In UVM:** `analysis_port.write()` is **synchronous** — it calls all subscribers' `write()` methods in sequence before returning. So as long as the monitor doesn't mutate the handle until after `ap.write()` returns, all `sample()` calls see the same data.

**The actual risk:**
- Monitor reuses the same seq_item across transactions (rather than building a fresh one each time).
- After `ap.write()` returns, monitor mutates fields for the next transaction.
- If the subscriber **deferred** sampling (e.g., used a `fork`), the cross would see mixed data.

**Defense:**
- Monitor clones the seq_item before each `ap.write()`: `i2c_seq_item cloned = i2c_seq_item::type_id::create("cloned"); cloned.copy(t); ap.write(cloned);`.
- Subscriber clones in `write()` if it intends to sample asynchronously.

**Interview-grade answer:**

> *"`analysis_port.write()` is synchronous — all subscribers run to completion before the port returns control to the monitor. Within a single `write()` call, all `sample()` invocations see consistent data because nothing else has touched the handle. The race emerges only if (a) the subscriber forks an asynchronous sample, or (b) the monitor reuses the same seq_item handle and mutates it for the next transaction immediately after `write()` returns — in which case any deferred coverage call would see the wrong data. Defense: clone the seq_item in the monitor before each `ap.write()`, so subscribers and scoreboards each get an immutable snapshot."*

### Q14 — What Makes a Good Covergroup

**Four properties:**

1. **Compact.** Bins are bucketed, not raw-valued. A coverpoint with 256 auto-bins is wasteful; a coverpoint with 4 semantic buckets (low, mid, high, max) is purposeful.

2. **Meaningful.** Each bin corresponds to a **distinct scenario in the verification plan**. If you can't articulate "what does it mean when this bin is hit," delete the bin.

3. **Non-redundant.** Two covergroups measuring the same thing with different bucketing is technical debt. Pick one bucketing scheme, justify it, stick with it.

4. **Connected to test plan.** Every bin should trace to a verification-plan line item. Coverage with no traceability is decoration.

**Bonus properties:**
- **Cross-aware.** Where interactions matter, use crosses. Don't multiply 1D coverpoints; multiply binsets.
- **Closable.** Bins should be reachable through stimulus. Unreachable bins should be `ignore_bins` with a documented reason.

**Interview-grade answer:**

> *"A good covergroup is compact — buckets values into semantically meaningful ranges rather than per-value bins; meaningful — every bin maps to a distinct test plan scenario; non-redundant — doesn't duplicate measurement found in another covergroup with different bucketing; and traceable — each bin maps back to a verification plan requirement. A bad covergroup has 256 auto-bins on a wide field, multiple covergroups measuring the same thing with overlapping buckets, or bins that look impressive in a report but don't connect to any spec scenario."*

### Q15 — Controlling Cross Bin Explosion

**Three techniques:**

**(a) Bucket the underlying coverpoints first.**
Instead of 8-bit auto-bins (256 bins each, 65K cross), use 4-bucket ranges (4 × 4 = 16 cross bins).

```systemverilog
cp_a: coverpoint a {
  bins low = {[0:63]}; bins midlow = {[64:127]};
  bins midhigh = {[128:191]}; bins high = {[192:255]};
}
// Repeat for cp_b. Cross = 4 × 4 = 16 bins.
```

**(b) Use `binsof` / `intersect` to limit the cross.**
```systemverilog
cross cp_a, cp_b {
  bins critical_combos = binsof(cp_a.high) && binsof(cp_b.high);
  ignore_bins boring   = !(binsof(cp_a.high) && binsof(cp_b.high));
}
```

**(c) Decompose into multiple 2-way crosses instead of one N-way cross.**
A 3-way cross of N each = N³ bins. Three pairwise crosses = 3 × N² bins. If pairwise interaction coverage is sufficient (often is per "pairwise testing" literature), you save dramatically.

**Bonus (d): `option.cross_auto_bin_max`** — caps the number of auto-bins created within the cross.

**Interview-grade answer:**

> *"Three techniques: first, bucket the underlying coverpoints into 4-8 semantic bins before crossing — this is the most important; auto-binning wide fields and then crossing them is the #1 cause of bin explosion. Second, use `binsof` and `intersect` inside the cross block to select only meaningful combinations and `ignore_bins` the rest. Third, decompose a 3-way cross into three pairwise 2-way crosses when pairwise interaction is sufficient — by pairwise testing theory, 80%+ of interaction bugs surface in 2-way coverage. Also `option.cross_auto_bin_max` caps explosion when one cross dimension is unbinned. The general principle: never let a cross's bin count exceed what your regression can realistically hit with reasonable stimulus."*

## 15. Key Takeaways

### Conceptual

1. **Functional coverage measures spec intent; code coverage measures structural execution.** Both required for signoff; neither alone is sufficient.

2. **Covergroups inside classes need explicit `new()`.** Forgetting it gives 0% coverage or null-pointer crash. The #1 silent failure mode.

3. **`ignore_bins` excludes from measurement; `illegal_bins` excludes AND fires runtime error.** Different roles — pick the right one.

4. **Cross coverage = Cartesian product of bins.** N-way cross = product of bin counts. Bucket coverpoints before crossing.

5. **Sampling can be event-driven (`@(posedge clk)`) or explicit (`cg.sample()`).** Use explicit for UVM subscriber patterns; events for RTL-embedded coverage.

6. **0% coverage with passing tests = wiring problem.** Always check the analysis_port → analysis_export connection first.

7. **Coverage closure is 100% minus documented waivers.** Raw 100% is rarely achievable and not the real signoff goal.

8. **Cross-bin explosion is a career-killer bug.** Bucket aggressively before crossing; use `binsof`/`intersect` to limit; decompose N-way into pairwise.

### Career-Critical

- **You WILL be asked covergroup questions in DV interviews.** The big ones: (a) functional vs code, (b) ignore_bins vs illegal_bins, (c) cross bin count math, (d) sampling mechanisms, (e) why is coverage 0%. Memorize Q1, Q4, Q3, Q5, Q7 answers.

- **A coverage class connected to the monitor is the single most-asked UVM pattern.** Know it cold: subscriber extends `uvm_subscriber #(T)`, override `write()`, connect in env's `connect_phase`.

- **Knowing transition bins separates you from the crowd.** Most freshers know auto-bins and ranges. Adding `(STATE_A => STATE_B [*2:5])` syntax in an interview is a senior-level signal.

- **Coverage is THE bridge between spec and silicon.** Engineers who deeply understand it move into architecture, verification leads, and tape-out signoff roles.
